# 飞书说明类文档（教学化 + mermaid 辅助）

本技能把"难读的工程规范 / 架构设计 / 代码核查结果"重组成"读者能看懂、愿意看下去"的飞书文档。

## 适用场景

- 把 spec / 设计文档 / 架构文档 / 代码审查结果整理成团队深读材料
- 用户说"这个文档难读，整理一下让人能懂"
- 把一份分析报告保存到飞书并要求可读性
- 任何"既要技术准确、又要好理解"的说明类文档

**不适用**：会议纪要、纯数据/表格搬运、逐字翻译、只需保留原文的场景。

---

## 写作前：必读依赖

执行任何 `lark-cli docs` 命令前，必须先读取 lark-doc skill：
- 认证与全局参数：`lark-shared/SKILL.md`
- XML 语法：`lark-doc/references/lark-doc-xml.md`
- 画板（mermaid/SVG）：`lark-doc/references/lark-doc-whiteboard.md`
- 更新工作流：`lark-doc/references/style/lark-doc-update-workflow.md`

**重要约束**：飞书 mermaid 画板只稳定支持 `flowchart TD` / `graph TD`（竖版有向图）。`sequenceDiagram` / `stateDiagram-v2` / `classDiagram` 等会触发 `degrade_code=2107 Whiteboard content parse failed`，不要用。

## 核心方法论：教学化四步

### 第 0 步　先给全局，不要一上来就堆细节

读者第一眼需要的是"这东西整体在干嘛"。在做任何分章细节前，先回答：
1. **一句话定位**：这东西是做什么的、解决什么问题。
2. **一张总览图**（mermaid flowchart TD，竖版）：把主要角色和数据流画出来。
3. **核心术语 / 交接物速查表**：把后面反复出现的关键名词集中解释一次。

> 心法：第 0 章建立"地图"，后面每章都是在放大地图的某一段。

### 第 1 步　用一个完整流程把全貌串起来

把"端到端走一遍"作为主线章节（通常是生命周期、调用链、一次请求的完整流程），按 ①②③ 编号逐步推进。让读者顺着一条主线把所有角色都见过一遍。

**这一步优先于深入细节**。读者先有全局骨架，后面填肉才不会迷路。

### 第 2 步　再分章深入

每深入一个组件/层/模块，固定包含：
- **角色一句话**：它是谁、负责什么。
- **一张图**：它的内部结构或状态流转（mermaid 竖版）。
- **关键设计 / 易错点 / 红线**：用 `callout` 高亮框标出"最容易踩的坑"和"绝对不能违反的规则"。
- **代码事实 / 不变量**：技术准确性的内容（代码引用、不变量编号、状态名）原样保留，不删减、不口语化。

### 第 3 步　收尾给速查

- **不变量 / 红线速查**：把散落各处的硬约束集中成一节，便于回查（可用 grid 多栏 callout 并排）。
- **实现状态 / 差距清单**：如实标注哪些已实现、哪些是占位/未实现，用表格。

## 结构骨架（可直接套用）

```
标题（带"图解/教学版"字样，区别于原始规范）

callout 📚：这篇文档怎么读（阅读路径 + 图都是竖版说明）
callout 📌：背景（来源 spec / 代码核查 / 适用范围）

第 0 章　先建立全局心智模型
  - 0.1 各部分各干什么（职责表 + 打比方）
  - 0.2 全貌协作图（mermaid flowchart TD）+ 交接物速查表

第 1 章　从一个 X 出发：完整生命周期/流程
  - 竖版流程图（mermaid）
  - ①②③... 逐步推进，每步配简短说明

第 2~N 章　深入各组件/层
  - 角色定位（blockquote）
  - 内部结构 / 状态机图（mermaid 竖版）
  - 关键设计 + 易错点 callout（⚠️）+ 红线 callout（🚫）
  - 技术事实原样保留（代码、不变量编号、表格）

收尾章
  - 不变量/红线速查（grid 多栏 callout）
  - 实现差距清单（表格）
  - 来源 callout（📝）

全程用 callout 标注重点，让读者扫读时能抓到信号：
  💡 提示 / ⚠️ 易错点 / 🚫 红线 / 📌 要点 / ❌ 未实现 / 📝 来源
```

## mermaid 使用规范（关键，避坑）

飞书 mermaid 画板渲染约束强，务必遵守：

### 1. 只用竖版 flowchart TD / graph TD

```
<whiteboard type="mermaid">
flowchart TD
    A[开始节点] --> B[第二步]
    B --> C[结束节点]
</whiteboard>
```

- **方向固定 `TD`（top-down，竖版）**，不要用 `LR`（横版太长，元素被压小，用户明确反对）。
- 时序/状态机等关系，**改用 flowchart TD 模拟**（用节点 + 箭头 + decision 节点 `{"条件 ?"}` 表达分支）。

### 2. 节点文字语法避坑（用户反复强调）

- ✅ 节点标签用**方括号文字**：`A[用户发消息] --> B[Daemon 处理]`
- ❌ **不要出现 `[]` 里包含 `()`**：`A[func(x)]` 会解析失败。
- ❌ **不要用 `["...\n..."]` 写换行**：`/n` 或字面 `\n` 是语法错误。
- ✅ 多行文字用 `<br/>`：`A["第一步<br/>写说明"]`。
- ✅ 含特殊字符（`/`、`∩`、`>`）的标签用**双引号包裹**：`A["Observed ∩ Desired"]`。
- ✅ XML 里 `>` 要写成 `&gt;`（标签内文本转义），`<` 写成 `&lt;`，`&` 写成 `&amp;`。

### 3. 节点不要太多太密

- 单张图节点 ≤ 15 个；超了就**拆成多张聚焦小图**，别塞一张大图。
- 文字简短，长说明放正文，图只表达"谁连到谁、分支在哪"。

### 4. 降级兜底

如果遇到 `degrade_code=2107 Whiteboard content parse failed`（飞书画板服务偶发降级），**先用竖版文字流程图兜底**，保证内容不丢：

```xml
<pre lang="Plaintext" caption="XX 流程（竖版）"><code>第一步<br/>   ↓<br/>第二步<br/>   ├─→ 分支A<br/>   └─→ 分支B</code></pre>
```

兜底后如实告知用户"飞书 mermaid 服务降级，这几处先用文字流程图，服务恢复后可补成图形"。

## 通用写作准则

1. **技术准确性 > 可读性 > 美观**。简化表达可以，但状态名、不变量编号、代码引用、数值**一个字都不能改**。一旦不确定，去核对源 spec / 代码再写。
2. **先全局后细节**。不要按原文顺序逐条搬运；按"读者理解顺序"重组。
3. **用 callout 给信号**。重点、易错、红线、未实现用不同 emoji callout 标出，让扫读也能抓重点。
4. **竖版优先**。所有图、长流程都竖版排布，适配窄屏。
5. **该长则长，不要硬压**。多段说明不要压成一行；用真实换行，不要用 `\n` 转义。
